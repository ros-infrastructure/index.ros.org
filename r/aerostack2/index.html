README

Website · Discussions · Issues

Aerostack2 is an open source framework for developing multi-robot aerial systems, built on ROS 2.

  • ROS 2 native. Every component is a ROS 2 node with standard topics, services and actions.
  • Modular. Controllers, state estimators, behaviors and planners are plugins you can swap without touching the rest of the stack.
  • Platform independent. The same mission runs in simulation and on real aircraft, so moving from sim to real is a configuration change.
  • Behavior based. Missions are built from reusable behaviors, driven from Python or behavior trees.
  • Swarm ready. Multi-drone namespacing and coordination are part of the design, not an add-on.

CONTRIBUTING

Contributing to Aerostack2

Thanks for getting involved! This page explains how to open an issue, a discussion or a pull request. Step-by-step guides are on the website: opening an issue and opening a pull request.

Aerostack2 is maintained by a small team, mostly alongside research work. A few minutes reading this page saves everyone time.

Understand your change

You must understand the code you submit. If you can’t explain what your change does and how it interacts with the rest of the stack, it isn’t ready.

AI tools are welcome. Read the AI Usage Policy before using them for a contribution.

Quick guide

I want to contribute

Pick an open issue and comment that you’re working on it. Issues labelled starter are a good first step. If you need help, ask on the issue.

I found a bug

Search open and closed issues first, it may already be fixed. If it hasn’t been reported, open a bug report and fill in the template completely, including the ROS distro, platform and steps to reproduce.

If an open issue already matches your problem, react with 👍 instead of commenting “same here”. Comment only when you have new information, such as logs or another way to reproduce it.

I have an idea for a feature

New features, new packages and architecture changes start with a feature request or an Ideas discussion. Agree on the design and where it fits before you write the code. Pull requests for these changes without a prior agreement will be closed.

I have a fix or a small improvement

Bug fixes and small improvements can go straight to a pull request. Link the issue it addresses, if there is one.

I have a question

Ask in Q&A. Please don’t open an issue for questions.

Pull requests

  • Keep each pull request to one change. Split unrelated fixes and refactors into separate pull requests.
  • Fill in the pull request template, including the distro and platform you tested on.
  • Pull requests are not the place to discuss design. Use the feature request or discussion and link your branch there.
  • All CI checks must pass before review.

Commit messages

Commits and PR titles follow Conventional Commits, for example feat(as2_core): add a filterable TF listener. The scope is optional.

Local hooks

Install the git hooks once per clone:

pixi run -e lint lefthook install

On every commit this checks the message and runs the ament linters (uncrustify, cpplint, flake8, pep257, xmllint) on the staged files. To lint the whole repository, run pixi run -e lint lefthook run pre-commit --all-files.

I want to contribute

Pick an open issue and comment that you’re working on it. Issues labelled starter are a good first step. If you need help, ask on the issue.

Search open and closed issues first, it may already be fixed. If it hasn’t been reported, open a bug report and fill in the template completely, including the ROS distro, platform and steps to reproduce.

If an open issue already matches your problem, react with 👍 instead of commenting “same here”. Comment only when you have new information, such as logs or another way to reproduce it.

I have an idea for a feature

New features, new packages and architecture changes start with a feature request or an Ideas discussion. Agree on the design and where it fits before you write the code. Pull requests for these changes without a prior agreement will be closed.

I have a question

Ask in Q&A. Please don’t open an issue for questions.

Pull requests

  • Keep each pull request to one change. Split unrelated fixes and refactors into separate pull requests.

  • Pull requests are not the place to discuss design. Use the feature request or discussion and link your branch there.

Aerostack2 is an open source framework for developing multi-robot aerial systems, built on ROS 2.

  • ROS 2 native. Every component is a ROS 2 node with standard topics, services and actions.
  • Modular. Controllers, state estimators, behaviors and planners are plugins you can swap without touching the rest of the stack.
  • Platform independent. The same mission runs in simulation and on real aircraft, so moving from sim to real is a configuration change.
  • Behavior based. Missions are built from reusable behaviors, driven from Python or behavior trees.
  • Swarm ready. Multi-drone namespacing and coordination are part of the design, not an add-on.

Contributing to Aerostack2

Thanks for getting involved! This page explains how to open an issue, a discussion or a pull request. Step-by-step guides are on the website: opening an issue and opening a pull request.

Aerostack2 is maintained by a small team, mostly alongside research work. A few minutes reading this page saves everyone time.

Understand your change

You must understand the code you submit. If you can’t explain what your change does and how it interacts with the rest of the stack, it isn’t ready.

AI tools are welcome. Read the AI Usage Policy before using them for a contribution.

Quick guide

I want to contribute

Pick an open issue and comment that you’re working on it. Issues labelled starter are a good first step. If you need help, ask on the issue.

I found a bug

Search open and closed issues first, it may already be fixed. If it hasn’t been reported, open a bug report and fill in the template completely, including the ROS distro, platform and steps to reproduce.

If an open issue already matches your problem, react with 👍 instead of commenting “same here”. Comment only when you have new information, such as logs or another way to reproduce it.

I have an idea for a feature

New features, new packages and architecture changes start with a feature request or an Ideas discussion. Agree on the design and where it fits before you write the code. Pull requests for these changes without a prior agreement will be closed.

I have a fix or a small improvement

Bug fixes and small improvements can go straight to a pull request. Link the issue it addresses, if there is one.

I have a question

Ask in Q&A. Please don’t open an issue for questions.

Pull requests

  • Keep each pull request to one change. Split unrelated fixes and refactors into separate pull requests.
  • Fill in the pull request template, including the distro and platform you tested on.
  • Pull requests are not the place to discuss design. Use the feature request or discussion and link your branch there.
  • All CI checks must pass before review.

Commit messages

Commits and PR titles follow Conventional Commits, for example feat(as2_core): add a filterable TF listener. The scope is optional.

Local hooks

Install the git hooks once per clone:

pixi run -e lint lefthook install

On every commit this checks the message and runs the ament linters (uncrustify, cpplint, flake8, pep257, xmllint) on the staged files. To lint the whole repository, run pixi run -e lint lefthook run pre-commit --all-files.

Contributing to Aerostack2

Thanks for getting involved! This page explains how to open an issue, a discussion or a pull request. Step-by-step guides are on the website: opening an issue and opening a pull request.

Aerostack2 is maintained by a small team, mostly alongside research work. A few minutes reading this page saves everyone time.

Understand your change

You must understand the code you submit. If you can’t explain what your change does and how it interacts with the rest of the stack, it isn’t ready.

AI tools are welcome. Read the AI Usage Policy before using them for a contribution.

Quick guide

I want to contribute

Pick an open issue and comment that you’re working on it. Issues labelled starter are a good first step. If you need help, ask on the issue.

I found a bug

Search open and closed issues first, it may already be fixed. If it hasn’t been reported, open a bug report and fill in the template completely, including the ROS distro, platform and steps to reproduce.

If an open issue already matches your problem, react with 👍 instead of commenting “same here”. Comment only when you have new information, such as logs or another way to reproduce it.

I have an idea for a feature

New features, new packages and architecture changes start with a feature request or an Ideas discussion. Agree on the design and where it fits before you write the code. Pull requests for these changes without a prior agreement will be closed.

I have a fix or a small improvement

Bug fixes and small improvements can go straight to a pull request. Link the issue it addresses, if there is one.

I have a question

Ask in Q&A. Please don’t open an issue for questions.

Pull requests

  • Keep each pull request to one change. Split unrelated fixes and refactors into separate pull requests.
  • Fill in the pull request template, including the distro and platform you tested on.
  • Pull requests are not the place to discuss design. Use the feature request or discussion and link your branch there.
  • All CI checks must pass before review.

Commit messages

Commits and PR titles follow Conventional Commits, for example feat(as2_core): add a filterable TF listener. The scope is optional.

Local hooks

Install the git hooks once per clone:

pixi run -e lint lefthook install

On every commit this checks the message and runs the ament linters (uncrustify, cpplint, flake8, pep257, xmllint) on the staged files. To lint the whole repository, run pixi run -e lint lefthook run pre-commit --all-files.
